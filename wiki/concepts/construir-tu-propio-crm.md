# Si algún día querés armar tu propio CRM — qué ya aprendimos que sirve de blueprint

**Qué es**: esta página no describe algo que exista — es una síntesis, pensada específicamente para el objetivo de largo plazo del usuario ("armar mi propio CRM"), de qué piezas de rmsystemm/DKW System funcionan bien y valdría la pena copiar el CONCEPTO (no el código, nunca se vio el código real), y qué falencias reales de la plataforma actual convendría no repetir.
**Fuente primaria**: todas las páginas de `entities/` de esta wiki, más [[24-sesion-2026-09-14-traspaso]] §4 (la investigación de reventa/white-label).

## Lo primero: rmsystemm es una marca sobre una plataforma de un tercero (DKW System)
Confirmado con 3 evidencias técnicas independientes (favicon en el storage del fabricante bajo un UUID de partner, prefijos de CSS `dkw-` en el HTML, la API real vive en `api.integrador-crm.com` no en un dominio de RM System). Esto significa dos cosas útiles para vos: (1) lo que hizo RM System (poner marca propia sobre DKW) se puede hacer igual — DKW vende explícitamente un programa de partner white-label; (2) el soporte con el que se habla hoy es el revendedor, no quien controla el producto de fondo — algunos bugs (guardrails, editor de Slate) dependen de una capa que no está bajo tu control aunque construyas tu propio CRM sobre la misma base. Si el objetivo es control total, la alternativa real es construir desde cero (más trabajo, cero dependencia de un tercero) o ser partner directo de DKW en vez de sub-revendedor.

## Piezas del diseño que SÍ funcionan bien y vale la pena copiar el concepto

- **Separación Pipeline (Kanban) / Cola / Canal / Agente, todos como entidades independientes que se conectan entre sí**, no un monolito. Un agente no "pertenece" a una pipeline — se vincula a una conversación puntual, lo que habilita rollout controlado real (ver [[agentes-legado-9882-9883-9884]]) sin tener que arriesgar tráfico real desde el primer día.
- **El motor de Flujos de Automatización** (ver [[flujos-de-automatizacion]]): un constructor visual de nodos (gatillo → condicional → acción) separado de las automatizaciones simples de columna, con nodos genéricos reusables (Data & Hora, Script, Requisição HTTP, Para cada item) es un patrón de automatización sólido y extensible — vale la pena como referencia de diseño si se construye algo propio.
- **Modo Clásico (analizador de acciones separado de la redacción) como antecedente de una arquitectura tipo Fit Brain** (ver [[fit-brain-vision]] y [[guardrails-y-analizador]]): separar "decidir qué hacer" de "redactar la respuesta" en dos pasos/llamadas es un patrón real, no solo teórico — la plataforma ya lo implementa de forma chica.
- **Guardrails como capa determinista posterior a la generación**, separados de las reglas de negocio del prompt — el criterio de "qué va en guardrail vs. qué va en prompt" (ver [[guardrails-y-analizador]]) es aplicable a cualquier sistema de agentes, no es específico de esta plataforma.
- **Un catálogo de acciones (chips) con nombres de función reales y documentados** (`save_variable`, `transfer_order`, `transfer_ticket`, `create_order`, `http_request`, `close_ticket`...) es más mantenible que texto libre interpretado — permite auditar qué puede hacer un agente sin leer todo el prompt.

## Falencias reales que NO conviene repetir si se construye algo propio

- **El editor de texto enriquecido (Slate.js) es frágil de verdad** — desincronización entre el DOM visible y el estado real del formulario (ver [[editor-slate-instrucciones]]), atomicidad de elementos "void" que rompe con ediciones parciales mal hechas. Un editor de prompts propio debería ser, como mínimo, un `<textarea>` plano con un preview aparte para los "chips", no un editor WYSIWYG complejo sobre el mismo campo que se envía al modelo.
- **Guardrails que no persistían (bug real, confirmado por el backend) sin ningún workaround del lado del cliente** — cualquier sistema de reglas de negocio necesita persistencia verificada en cada guardado, no solo un botón "Guardar" que parece funcionar.
- **La invocación del agente puede fallar en silencio, sin ningún log** (ver [[agente-recepcionista-comercial-10005]], Q26) — un sistema propio necesita observabilidad real de "¿se intentó procesar este mensaje? ¿qué pasó?" desde el día uno, no como algo agregado después. Esto conecta directo con A18 (observabilidad) en `PENDIENTES.md`.
- **Vincular un agente a una conversación no lo hace procesar el último mensaje ya existente** (ver [[agentes-legado-9882-9883-9884]], A33) — un handoff entre agentes necesita, por diseño, que el agente nuevo pueda reprocesar el estado actual sin depender de que llegue un mensaje nuevo del cliente.
- **La API expone tokens/secretos en texto claro en payloads que no deberían llevarlos** (el `metaToken` en cada mensaje, ver [[seguridad-incidentes]]) — separar claramente qué campos son de solo-lectura pública vs. cuáles deberían nunca salir del backend.
- **Ambigüedad de nombres entre lo que el prompt escribe y lo que el sistema realmente tiene guardado** (espacios en nombres de columna, ver [[pipelines-y-columnas]]) — un sistema propio debería resolver referencias por ID interno, nunca por coincidencia de texto libre entre el prompt y la configuración real.

## La arquitectura de agentes en sí (llevable a cualquier CRM, no depende de rmsystemm)
Todo el trabajo de [[arquitectura-conversacional]] — descubrimiento vs. puente, verdad comercial vs. afirmación del cliente, STOP SELLING, seguridad como override total, no narrar la memoria — es lógica de producto, no de plataforma. Es exactamente lo que habría que reimplementar tal cual en un CRM propio, y ya está probado con conversaciones reales acá.
