# Registro de Cambios y Evolución del Proyecto

## Qué es este archivo
Registro cronológico de las sesiones de trabajo sobre este vault y sobre el proyecto "Agente Fit". Sirve para que, al retomar el trabajo desde otra PC, se pueda entender rápido qué se hizo, qué se decidió y qué quedó pendiente, sin tener que reconstruir todo desde el historial de commits. Se actualiza al cierre de cada sesión con cambios relevantes, y se sube a GitHub (`origin/main`) para que quede disponible en cualquier máquina.

## Cómo usarlo
- Cada sesión nueva se agrega **arriba de todo** (orden cronológico inverso), con fecha real en formato `AAAA-MM-DD`.
- Cada entrada resume: qué se pidió, qué se verificó/hizo, qué se decidió, qué queda pendiente.
- Los pendientes de fondo del proyecto (no de este registro) siguen viviendo en [[06-seguridad-y-pendientes]].

### 2026-09-13 (continuación) — Flujo nuevo: Alerta de Stock Bajo (construido junto al usuario, paso a paso)
- **Pedido**: el usuario preguntó si el agente iba a poder avisar cuando haya que reponer stock. Se aclaró la distinción: eso no lo hace el Agente de IA conversacional, sino que hace falta una automatización aparte (tipo la de renovación de token) que consulte Bling y avise al equipo.
- **Investigación previa (con llamadas reales a la API, no documentación inventada)**: se confirmó que `GET /Api/v3/produtos` ya trae un objeto `estoque` embebido (`{minimo, maximo, saldoVirtualTotal}`) — no hace falta un endpoint de stock separado. Hallazgo real: `minimo`/`maximo` están en `0` para todos los productos (no hay umbral cargado en Bling), y el campo `situacao` no sirve para distinguir "descontinuado" (todos los productos activos comparten el mismo código `"A"`). Se confirmó también, revisando `Minhas instalações` en Bling, que la cuenta tiene conectados Shopify y 2 integraciones de "Vendas presenciais" (POS) — el stock se descuenta solo cuando se vende por esos canales, no hace falta automatizar eso.
- **Decisiones del usuario**: umbral `< 3` unidades (sin filtrar descontinuados, acepta el ruido); WhatsApp a su propio número (+598 990 98325) para probar, con opción de pausarlo si no sirve; frecuencia 1x/día.
- **Construido, guiado paso a paso (el usuario hizo los clicks, yo indicaba)**: flujo **"FV|Bling - Alerta de Stock Bajo"** (id 5118), 10 nodos — Agendado (1x/día) → Criar contato (mismo "Sistema - Bling Token" que el flujo de renovación, para leer su `access_token`) → Salvar Variável (`alerta` = "") → Script (genera `[1..15]`, guardado en `{paginas}`) → Para cada item (loop sobre `{paginas}`) → [rama CADA ITEM: Requisição HTTP GET productos por página con `Authorization: Bearer {contact.extraInfo.Bling Access Token}` → Script que filtra stock bajo y acumula texto en `{alerta}`] → [rama CONCLUÍDO: Condicional `{alerta}` não está vazio → Criar contato (2, el admin) → Criar Conversa (Canal Fitness Suplementos) → Enviar Mensagem].
- **Hallazgos técnicos nuevos** (detalle completo en [[15-flujos-automatizacion-avanzados]]): "Script" no tiene `fetch`/red, solo transforma variables ya traídas; el patrón para acumular resultados entre iteraciones de "Para cada item" es un Script que se auto-referencia (`data.alerta` → lo extiende → lo vuelve a guardar como `{alerta}`), no existe un modo nativo "agregar a lista"; dejar el campo "Valor" de "Salvar Variável" vacío guarda la cadena literal `"undefined"`, no `""` (hay que blindar el Script que lo lee); "Enviar Mensagem" no tiene campo de destinatario propio (actúa sobre el "contato ativo") y además exige una "Conversa" creada antes, no alcanza con el contacto; el botón "Testar" de flujo completo NUNCA ejecuta HTTP real (dice explícitamente `não executada no teste`) — para probar de verdad hay que usar "Executar passo" por nodo, o dejar correr el flujo real.
- **Bug real encontrado y diagnosticado con el Histórico de Execuções**: la primera corrida real (no "Teste") del flujo se ejecutó bien pero se cortó en el nodo "Condicional" (nunca llegó a mandar el WhatsApp) porque el flujo de renovación de token de Bling (ver sesión anterior) **todavía no había corrido ninguna vez de verdad** (todas sus ejecuciones en el Histórico decían "Teste") — el campo "Bling Access Token" del contacto seguía vacío a propósito, así que la llamada a Bling falló en silencio (sin error visible) y `{alerta}` quedó siempre `""`. No es un bug del flujo nuevo, es una dependencia real entre los dos flujos que hay que tener presente.
- **Estado al cierre**: flujo publicado, horario final "Todo dia às 10:05". El usuario está seguro de que el flujo de renovación (activado de madrugada, ciclo de 5hs) ya va a haber corrido de verdad para esa hora. **Pendiente**: confirmar mañana si llegó el WhatsApp a las 10:05; si no llega, primer sospechoso es de nuevo el estado del `access_token` (revisar Histórico de Execuções del flujo 5117 para ver si ya tiene alguna ejecución real, no "Teste").
