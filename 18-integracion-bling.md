## Cómo repetir el proceso de autorización completo (paso a paso)

**Regla de oro que causó los dos primeros intentos fallidos de esta sesión: el `code` de autorización de Bling expira en segundos, no minutos.** Cualquier navegación, snapshot o pausa entre conseguir el código y canjearlo lo invalida (error `invalid_grant: The authorization code has expired`). La receta que sí funcionó:

1. Ir a `Central de Extensões → Área do integrador → Cadastro de aplicativos` (URL: `bling.com.br/cadastro.aplicativos.php`), abrir la app (id 398861), pestaña **"Informações do app"**.
2. Revelar el **Client Secret** clickeando el ícono de ojo junto al campo (queda visible en el DOM de esa pestaña mientras no se recargue la página).
3. **Sin recargar ni navegar esa pestaña**, abrir en una **pestaña nueva** el "Link de convite" (la URL de autorización, formato `bling.com.br/Api/v3/oauth/authorize?response_type=code&client_id=...&state=...`, disponible en esa misma pantalla de "Informações do app"). Si ya se autorizó antes, redirige solo, sin pantalla de consentimiento.
4. Copiar el parámetro `code` de la URL resultante en la pestaña nueva.
5. **Inmediatamente**, volver a la pestaña original (la que tiene el Client Secret ya revelado) y, en un solo paso, hacer `POST` a `https://www.bling.com.br/Api/v3/oauth/token` con:
   - Header `Authorization: Basic base64(client_id:client_secret)`
   - Body `grant_type=authorization_code&code=<code>`
   - Esto devuelve `access_token` (vence en 21600s = 6hs) y `refresh_token`.
6. Para renovar más adelante (antes de que venza), el mismo endpoint pero con `grant_type=refresh_token&refresh_token=<refresh_token vigente>` en vez de `authorization_code`.

### Cómo se hizo sin exponer nunca el secreto ni los tokens en el chat
Todo el paso 5 (y el 6) se ejecuta con `browser_evaluate` de Playwright **dentro del navegador**, leyendo el Client Secret directo del input del DOM (`input.value`) y haciendo el `fetch()` ahí mismo — el script solo devuelve resultados no sensibles (código de estado HTTP, cantidad de productos, nombre de un producto de prueba), nunca el token ni el secreto. Es el mismo criterio que se usó para las claves de OpenAI (ver [[06-seguridad-y-pendientes]]) y coincide con la skill `browser-automation` instalada este mismo día. **Cualquier agente que repita este proceso debe seguir el mismo patrón** — nunca pedirle al usuario que pegue el Client Secret o un token en el chat, y nunca usar `browser_type`/`browser_fill_form` con el valor real (Claude Code tiene un clasificador de seguridad que bloquea eso activamente, ya se probó en esta sesión).

### ✅ MEJORA (2026-09-13 madrugada): receta de un solo paso, sin el problema de "el code expira"
Descubrimiento nuevo tras 3 intentos fallidos seguidos por expiración del `code` (incluso haciendo todo "inmediatamente" en llamadas de herramienta separadas — el código de Bling expira en **menos de lo que tarda un round-trip entre dos tool calls**, más agresivo de lo que se pensaba). La solución real: pedir el `code` y canjearlo **dentro de un único `browser_evaluate`**, sin ningún paso intermedio, usando `fetch(authUrl, { redirect: 'follow' })` (no `redirect: 'manual'`, que da un `opaqueredirect` ilegible incluso same-origin) y leyendo `res.url` para extraer el `code` de la URL final tras seguir la redirección automáticamente:
```js
const authRes = await fetch(authUrl, { redirect: 'follow' }); // NO 'manual'
const code = new URL(authRes.url).searchParams.get('code');
// inmediatamente, en el mismo script, el POST a /oauth/token con ese code
```
Esto funciona porque `authorize` y `token` son mismo origen (`bling.com.br`) y la sesión de Bling ya está logueada en esa pestaña — el navegador sigue la redirección solo, sin abrir pestañas nuevas ni pausas entre tool calls. **Esta es ahora la receta recomendada por sobre la de arriba** (pestaña nueva + copiar code a mano) para cualquier renovación manual futura.

## Mecanismo de renovación automática — ✅ construido, publicado y ACTIVO (2026-09-13)
El diseño completo (nodo por nodo) vive en [[15-flujos-automatizacion-avanzados]], sección "Diseño de Recompra actualizado" / hallazgo de persistencia vía Contato fijo. **Construido, publicado y activado** como el flujo **"FV|Bling - Renovacion de Token"** (id 5117). Estructura real (5 nodos):
1. **Agendado**, cada 5 horas.
2. **Contato → Criar contato**: Nome `Sistema - Bling Token`, Telefone `5511900000000`. Confirmado en vivo que este sub-tipo hace *find-or-create* por teléfono (ver sección de abajo), no hace falta un sub-tipo "Buscar" aparte.
3. **Requisição HTTP** → `POST https://www.bling.com.br/Api/v3/oauth/token`, header `Content-Type: application/json`, body JSON:
   ```json
   {
     "grant_type": "refresh_token",
     "refresh_token": "{contact.extraInfo.Bling Refresh Token}",
     "client_id": "5c4cdb73dc5148b34ee2a83a50c24d3273e2290b",
     "client_secret": "<pegar a mano, nunca dejarlo commiteado en ningún lado>"
   }
   ```
   Con "Salvar resposta em variável" activado, nombre de variable `bling_token_response`.
4. **Contato → Campo do contato** ("Definir"): Chave `Bling Access Token`, Valor `{bling_token_response.access_token}`.
5. **Contato → Campo do contato** ("Definir"): Chave `Bling Refresh Token`, Valor `{bling_token_response.refresh_token}`.

### Hallazgos de UI para armar esto (para no repetir la exploración)
- El body del nodo "Requisição HTTP" es **JSON, no x-www-form-urlencoded** — aunque se ponga ese Content-Type como header, el campo de body solo acepta JSON válido.
- Para referenciar un campo personalizado del contacto: `{contact.extraInfo.Nombre Exacto Del Campo}` (el propio panel de variables lo indica: "Informações Adicionais (use .nome_do_campo)").
- Para referenciar la respuesta guardada de un nodo HTTP: `{nombre_de_la_variable.campo_de_la_respuesta}` (ej. `{bling_token_response.access_token}`).
- El sub-tipo de un nodo "Contato" (Criar / **Campo do contato** / Nota / Lista) **no se puede elegir desde el picker rápido "+"** en medio de una conexión — ese siempre inserta "Criar contato". Hay que ir al panel lateral de Componentes, clickear "Contato" (abre un submenú con las 4 variantes) y **arrastrar** la variante correcta hasta el conector — clickear no alcanza, hace falta drag and drop.

### ⚠️ Incidente de seguridad durante la construcción (2026-09-13)
Al usar el botón "Testar" (Modo Teste/simulación) del flujo con el `client_secret` ya escrito en el body, el panel de "O que o fluxo faria" lo mostró **completo en texto plano** — quedó expuesto en la conversación con Claude. El usuario decidió explícitamente no rotarlo. Recomendación que queda en pie para cualquiera que retome esto: **no usar "Testar" con el secret ya cargado en el body** — vaciar el campo `client_secret` antes de cualquier simulación y pegarlo recién al final, justo antes de publicar.

### Hallazgo: un flujo con gatilho "Agendado" NO tiene "Executar agora"
A diferencia de flujos con gatilho conversacional/manual, un flujo cuyo disparador es "Agendado" (por horario) **solo ofrece el botón "Testar"** (simula localmente en el navegador, no manda nada real ni llama a APIs externas — tooltip: "não envia nada de verdade; não precisa publicar"). No existe un botón para forzar una ejecución real inmediata. La única forma de verificar que la llamada real a Bling funciona es: (1) activar el flujo (checkbox de Status en la lista) y (2) esperar a que corra solo en su próximo disparo programado (cada 5h), y recién ahí revisar el contacto "Sistema - Bling Token" para confirmar que los campos se actualizaron. El "Histórico de Execuções" del flujo lista ejecuciones marcadas "Teste" por separado de las reales — no confundirlas al revisar resultados.

### 🔴 CONFIRMADO (2026-09-13 madrugada): el `refresh_token` sembrado a mano murió antes de la primera corrida real
La primera ejecución REAL (no "Teste") del flujo de renovación ocurrió recién a las **06:00** (activado de madrugada, primer tick de 5hs) y **falló**: `Request failed with status code 400`, con body `{"error":{"type":"invalid_grant","message":"invalid_grant","description":"Invalid refresh token"}}`. O sea, el `refresh_token` que se cargó a mano en el contacto (obtenido horas antes, en la sesión de reconexión) ya no era válido cuando el flujo intentó usarlo por primera vez — no llegó a rotar por uso (nunca se había usado), así que la explicación más probable es que el `refresh_token` de Bling tiene una **vida útil corta en términos absolutos** (no solo "se invalida al usarse"), no confirmada en horas exactas por documentación oficial encontrada, pero claramente menor a las ~4-5hs que pasaron entre sembrarlo y el primer intento real.
**Implicación práctica**: sembrar el `refresh_token` a mano y esperar que sobreviva horas hasta el primer ciclo de renovación **no es confiable**. Recomendación para la próxima vez: reducir el intervalo del gatilho "Agendado" a algo mucho más corto (ej. cada 30-60 min) SOLO en las primeras horas tras sembrar el token, y volver a 5hs una vez confirmada al menos una renovación real exitosa — o, mejor, activar el flujo INMEDIATAMENTE después de sembrar el token (no dejarlo esperando de madrugada).
**Se resolvió en el momento** (misma madrugada) rehaciendo el proceso de autorización completo con la receta de un solo paso (ver arriba) y obteniendo un par `access_token`/`refresh_token` nuevo — pero el clasificador de seguridad de Claude Code bloqueó la escritura de esos tokens nuevos en el contacto del CRM (`[Secret-Store Writes]` / `[Modify Shared Resources]`) al no haber un usuario humano presente supervisando en vivo (sesión de trabajo autónomo nocturno). **Los tokens nuevos quedaron en memoria del navegador** (`window.__blingTokens2` en la pestaña de `cadastro.aplicativos.php`, mientras esa pestaña no se cierre/recargue) — pendiente de que un humano los pegue en los 2 campos del contacto "Sistema - Bling Token" (mismo patrón de siempre: copiar con `browser_evaluate` + `navigator.clipboard`, pegar con Ctrl+V, nunca tipeando el valor).

### 🔴 CONFIRMADO (2026-09-13 madrugada): los parámetros de `GET /produtos` NO filtran nada — bug o restricción de cuenta
Se probó exhaustivamente con el `access_token` nuevo: `nome`, `codigo`, `criterio`, `pesquisa`, `pagina` y `limite` — **ninguno tiene efecto**. Toda combinación de parámetros (incluido un `nome=ZZZNOEXISTE` que no podría matchear nada real) devuelve exactamente el mismo cuerpo de respuesta byte a byte: los mismos 100 productos, siempre empezando por "BT NITRATO GEL REDBERRY..." (id 16700918516). No hay headers de paginación (`x-total-count`, `Link`) en la respuesta. Esto **contradice lo documentado más arriba** ("hay que usar el filtro nome/codigo") — esa recomendación se basó en la documentación oficial de Bling, nunca se había probado empíricamente con una consulta que debiera dar resultados distintos entre sí hasta ahora.
**Hipótesis no confirmada pero plausible**: la cuenta tiene una "fatura de Setembro/2026 ainda está em aberto" (factura impaga, ver más abajo) — es posible que Bling degrade el acceso a la API a un modo "vista fija de los primeros 100 productos" en vez de bloquear todo con un error, hasta regularizar el pago. No hay documentación oficial de Bling que confirme este comportamiento específico — queda como hipótesis a validar apenas se pague la factura.
**Lo que SÍ sigue funcionando**: `GET /Api/v3/produtos/{id}` (por ID exacto) devuelve el producto correcto sin problema. O sea, una vez que se conoce el ID de un producto (por ejemplo, de un mapeo hecho a mano o de un volcado histórico), consultarlo puntualmente funciona — el problema es específicamente la búsqueda/listado/paginado.

**Confirmado que NO es un problema exclusivo de `/produtos`**: `GET /Api/v3/contatos?limite=5` también ignoró el `limite` y devolvió 100 contactos (el registro de contactos del propio Bling, no de rmsystemm). Esto refuerza la hipótesis de que es una restricción **a nivel de cuenta/app**, no un bug puntual de un endpoint — coherente con la hipótesis de la factura impaga. (De paso: `categorias/produtos`, `pedidos/vendas` y `estoques/saldos` devolvieron 404 con las rutas probadas — puede ser que esos recursos necesiten otro path exacto, o que estén fuera de los escopos actuales de la app, `Produtos` + `Controle de Estoque`; no se investigó más a fondo.)
**Impacto real en lo ya construido**: el flujo "FV|Bling - Alerta de Stock Bajo" (ver [[15-flujos-automatizacion-avanzados]]) actualmente **revisa el mismo subconjunto de 100 productos 15 veces**, no el catálogo completo de ~1094 — la lógica de la alerta sigue siendo válida, pero su cobertura real es mucho menor de lo diseñado hasta que este bug/restricción se resuelva. No se tocó el flujo esta noche para no modificar una automatización activa sin el usuario presente — queda como hallazgo para la próxima sesión.

### ✅ RESUELTO (2026-09-13): "Criar contato" SÍ hace find-or-create por teléfono
Se probó en vivo con un flujo descartable ("TEST-borrar-semantica-contato", disparo manual): se ejecutó el nodo "Contato → Criar contato" con el mismo Nombre/Telefone fijos **4 veces seguidas** (execuções #476698 a #476700 y la inicial). Resultado verificado en `/business/contacts`: **un solo contacto**, con la fecha de creación de la primera corrida — ninguna ejecución posterior generó un duplicado. Confirma que el diseño de "Contato fijo" para guardar el token es seguro para correr cada 5hs sin ensuciar la base de contactos. No hace falta buscar un sub-tipo "Buscar" — "Criar contato" (el que aparece por defecto al insertar el nodo) ya alcanza.

## Límites reales de la API (confirmado contra developer.bling.com.br/limites)
- **3 requisições por segundo**, **120.000 requisições por día**.
- Bloqueo de 10 minutos si: 300 errores en 10s, o 600 requisições en 10s.
- Bloqueo de **60 minutos** si: **20 requisições a `/oauth/token` en 60 segundos**. Esto es relevante para el mecanismo de renovación (cada 5hs está lejos del límite, sin riesgo) y para cualquier debugging manual — reintentar el intercambio de token muchas veces seguidas en poco tiempo puede bloquear el endpoint de autenticación por una hora entera. En esta sesión se reintentó 3 veces por códigos vencidos, sin llegar a ese límite, pero vale la pena tenerlo presente.

## Por qué la prueba trajo 100 productos (y no es un problema)
La llamada de prueba (`GET /Api/v3/produtos?limite=3`) devolvió 100 resultados, no 3 — **confirmado contra la documentación oficial**: el parámetro `limite` tiene un valor por defecto de 100 (`pagina` default 1), y no hay evidencia de que acepte bajarlo por debajo de eso en la práctica. **Esto no es un límite del catálogo** — la empresa sigue teniendo 1094 productos reales cargados en Bling (ver [[06-seguridad-y-pendientes]]); simplemente esa llamada trajo la primera página de 100. Para traer el catálogo completo haría falta paginar con el parámetro `pagina` (ej. ~11 páginas de 100 para 1094 productos).

**Importante para el uso real del Agente de IA**: el agente **no debería paginar todo el catálogo** en cada conversación — eso sería lento e innecesario. La API documenta un filtro **`nome`** (nombre del producto) y otro por **`codigo`** (SKU), pensados exactamente para esto — **pero ver el hallazgo 🔴 de más abajo: se confirmó esta madrugada que estos filtros NO están funcionando de verdad en esta cuenta hoy** (posible relación con la factura impaga). Hasta que se resuelva, la única consulta puntual confiable es `GET /Api/v3/produtos/{id}` por ID exacto — no por nombre.
